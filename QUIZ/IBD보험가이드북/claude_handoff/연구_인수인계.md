# IBD Rx Agent 논문 연구 — 인수인계 (2026-11-09 기준)

이 문서는 다른 Claude 대화에서 이어서 작업할 수 있도록 지금까지의 연구 상태를 정리한 것이다. 같은 폴더의 파일 목록은 맨 아래에 있다.

---

## 1. 연구 질문

**2024 대한장연구학회(KASID) 염증성장질환 보험가이드북을 검색하는 RAG 에이전트가, 검색 없는 LLM보다 국내 급여 기준을 더 정확히 아는가?**

- 평가 대상 두 가지 (생성 모델은 같다: `gpt-5.6-terra`)
  - **Baseline**: 가이드북 본문 없이 질문만 받는 LLM
  - **에이전트**: 가이드북을 검색해 상위 5개 쪽을 근거로 답하는 RAG 시스템
- 문항은 단계별로 설계 중이다. 지금 끝난 것은 **A형(급여 기준을 아는가)** 뿐이다.
  - 다음 단계: **C형(환자 사례에 기준을 적용할 수 있는가)**, 아직 없음
  - A형과 C형은 `짝키`로 연결된다. A는 맞히고 C를 틀리면 "기준은 아는데 적용을 못 함"이다.

## 2. 시스템 구조 (에이전트)

FastAPI 백엔드(`backend/app/rag/`)와 React 프런트엔드로 구성된다.

| 단계 | 설정 |
|---|---|
| 코퍼스 | 가이드북을 쪽 단위로 나눈 69개 passage (`data/RAG/IBD_insurance_guide_2024.jsonl`) |
| 어휘 검색 | BM25 상위 12개. 한글은 단어와 2글자 조각, 영문은 소문자로 토큰화. 제목·약제·질환 메타데이터를 본문 앞에 붙임 |
| 의미 검색 | `text-embedding-3-large` 코사인 유사도 상위 12개 (FAISS 전수 검색) |
| 융합 | Reciprocal Rank Fusion (k=60), 후보 20개 |
| 재정렬 | `BAAI/bge-reranker-v2-m3` 크로스 인코더 |
| 생성 | 재정렬 상위 5개 쪽을 컨텍스트로 `gpt-5.6-terra`가 답함 |

평가 때 쓴 생성 프롬프트(`answer_only` 모드, `backend/app/rag/generate.py`의 `_ANSWER_ONLY`) 요지:
- 근거는 제공된 발췌뿐. 발췌에 없는 수치·조건·금기는 만들지 않는다.
- 첫 줄은 "답: "으로 시작하고 **핵심 답만** 적는다.
- 발췌에 그 기준이 없으면 "답: 가이드북에 적혀 있지 않다"라고만 쓴다.

별도로 규칙 기반 급여 판정 엔진(`backend/app/filtering.py`, `/api/eligibility`)이 있다. 환자 조건을 넣으면 약을 사용 가능 / 보류 / 제외로 나눈다. A형 평가에는 쓰지 않았다.

## 3. A형 문항

- 생성기: `STAGE1/make_a.py`. 가이드북 내용을 옮긴 CSV(44행)에서 문항을 만든다. API는 쓰지 않는다.
- **107문항, 고유 정답 54개.** 생성 전에 매번 자체 시험 33건을 돌리며, 지금은 모두 통과한다.
- 본 점수는 금기 6문항을 뺀 **101문항**이다. 금기 문항은 목록형이라 항목 재현율로 따로 본다.

| 기준 | 문항 | 예 |
|---|---|---|
| 나이 | 7 | [Infliximab IV, 장형 베체트] 연령 조건은? → 19세 이상 |
| 활성도 | 25 | [Adalimumab, UC] 급여 활성도 기준은? → Mayo 6~12 그리고 내시경 subscore 2 이상 |
| 이전 치료 | 25 | 어떤 이전 치료에 실패해야 급여되는가? |
| 유지 기준 | 25 | 유지요법은 언제, 어떤 조건에서 인정되는가? |
| 고령·고위험 | 7 | 65세 이상 환자에게 붙는 추가 조건? |
| 검사 하한 | 12 | Hb / ANC / ALC 하한은? |
| 금기 (보조) | 6 | 투여 전 체크리스트 항목을 모두 쓰시오 |

- 대조 문항 8개: 정답이 "가이드북에 적혀 있지 않다"인 문항이다. 기준을 지어내는지 확인하려고 넣었다.
- 자세한 설계와 채점 열쇠는 `STAGE1_README.md`에 있다.

## 4. 평가 방법

- 실행 스크립트는 `STAGE1/eval_a.py`이며 표준 라이브러리만 쓴다.
- Baseline에는 "2024 보험가이드북 기준으로 답만 말하라"는 지시와 답 형식만 준다.
- 에이전트에는 질문 문장만 보낸다(`answer_only: true`). 답 형식은 에이전트 프롬프트가 맡는다.
- **채점**: LLM 채점자 `gpt-6-sol`(평가 대상과 다른 모델)이 질문, 정답, 채점 열쇠, 모델 답을 보고 맞음 / 부분 / 틀림을 낸다.
  - 점수: 맞음 1, 부분 0.5, 틀림 0
  - 채점 규칙 요지: 뜻이 같으면 맞음. 숫자, 이상/초과, 그리고/또는이 다르면 틀림. 정답에 없는 조건을 **지어내면** 틀림이고, 맞는 답에 덧붙인 설명은 감점하지 않음.
  - 이전 치료 문항은 필수 요소 3개로 본다: 최소 가지 수, 치료 종류, 반응 조항(반응 없음 / 불내성 / 금기 / 부작용 중단).
  - **채점자는 가이드북 원문을 받지 않는다.** 아래 6절의 문제가 여기서 생긴다.
- 문항당 1회 실행했다. 실행 날짜: baseline 2026-10-26~27, 에이전트 2026-10-27.

## 6. 오류 분석 (2026-11-09)

에이전트가 정답을 다 맞히지 못한 **38문항**(본 점수 기준 틀림 19 + 부분 19)의 원인을 하나씩 확인했다. 문항별 내역은 `agent_오류분석_38문항.csv`에 있다.

| 원인 | 문항 수 |
|---|---|
| A. 검색 실패 (정답 쪽이 상위 5개에 없음) | 5 |
| B. 생성 오류 (정답 쪽이 검색됐는데 잘못 답함) | **23** |
| C. 채점 오류 (가이드북에 있는 사실을 덧붙였는데 감점됨) | 6 |
| D. 정답 기준 문제 (문항 범위) | 4 |

**핵심: 에이전트 점수를 가장 많이 깎는 것은 검색이 아니라 생성 단계, 즉 검색한 원문을 제대로 읽어내지 못한 것이다.**

### A. 검색 실패 5건: 질문 단어와 원문 단어가 달라서

| 질문 단어 | 원문 단어 | 결과 |
|---|---|---|
| Hb | 헤모글로빈 | 체크리스트 쪽(p.49, p.52)이 BM25에서 17~28위 |
| ALC | p.49 원문 오타 "절대 림프구수**(ANC)**" | p.49가 재정렬 후보 20개에도 못 들어감 |
| 유지요법 | UC·베체트 쪽은 "지속적인 투여" (CD 쪽만 "유지요법") | UC·베체트 질문에 CD 쪽(p.35, p.38)이 검색됨 |

- 질문의 한글 질환명("궤양성 대장염")이 BM25 점수를 많이 가져간다. 그런데 체크리스트 쪽에는 한글 질환명이 없고 메타데이터 "UC"만 있다.
- 검색 단계를 재현해 보면(BM25·벡터·RRF, 백엔드 코드 그대로) 성공한 TOF Hb와 실패한 FIL Hb의 융합 순위가 똑같이 15위였다. 재정렬에서 아슬아슬하게 갈렸다. 재정렬 단계는 로컬에 torch가 없어 재현하지 못했고, 최종 상위 5개는 평가 때 저장된 응답에서 가져왔다.
- 이 때문에 검사 하한에서 에이전트(0.67)가 baseline(1.00)보다 낮다.
- 백엔드에는 동의어나 질의 확장 처리가 없다.

### B. 생성 오류 23건

| 패턴 | 건수 | 예 |
|---|---|---|
| 반응 조항 잘림 | 14 | 원문 "적정한 반응을 나타내지 않거나 **내약성이 없는 경우 또는 상기 약제가 금기인**" → 답 "적정한 반응을 나타내지 않은 경우" |
| 대조 문항에서 기준을 만들어 냄 | 4 | 베체트 활성도를 물었는데 유지 기준 "DAIBD 20점 감소"로 답함 |
| 유지 기준 대신 투여 일정으로 답함 | 2 | IFX SC: p.38이 1위로 검색됐는데 "마지막 정맥주입 후 8주에 120mg" |
| 근거가 있는데 기권 | 1 | IFX SC UC 활성도: p.39에 "Mayo 6 to 12"가 있는데 "적혀 있지 않다" |
| 기타 | 2 | 평가 시점 누락, FIL ANC를 "미만"으로 답함 |

**반응 조항 잘림은 질환별로 갈린다.** 프롬프트와 질문 문장은 같은데 크론병 문항은 대부분 전체 조항을 쓰고, UC는 11문항 중 10개가 거의 같은 문장으로 잘린다. UC 원문은 조건이 "…금기인 중등도-중증의 궤양성 대장염 환자"처럼 환자 설명 안에 길게 박혀 있다. 여기에 질문이 "어떤 이전 치료에 **실패해야**"라고 묻는다.

가설: 질문 문구, 원문 구조, 프롬프트의 "핵심만" 지시가 겹친 결과다. **셋 중 무엇이 주원인인지는 아직 검증하지 않았다.** 검증 방법은 7절에 있다. 이 문구 문제는 baseline에도 똑같이 작용한다(baseline 이전 치료: 완전 정답 0, 부분 15).

### C. 채점자 문제

- **채점자는 일관적이다.** 두 실행에서 정답도 같고 답도 같은 묶음 26개 모두 판정이 같았다.
- 지금까지 찾은 채점 오류 약 15건은 원인이 두 가지뿐이다.
  1. **채점자가 가이드북 원문을 받지 않는다.** 그래서 덧붙인 내용이 지어낸 것인지 원문에 있는 것인지 구분하지 못하고, 모두 "지어냄"으로 처리했다(에이전트 6건, baseline 1건).
  2. **척도 범위를 모른다.** "Mayo 6점 이상"과 "6~12"는 Mayo 총점 최대값이 12라서 같은 뜻인데 틀림으로 처리했다(baseline 7건). 프롬프트에 "급여 기준을 스스로 다시 판단하지 마세요"가 있어서 글자 그대로 비교했다.
- **확인되지 않은 것**: 채점자가 틀린 답을 맞음으로 잘못 준 경우다. 지금까지는 점수를 올리는 방향만 검토했다.

### 보정(human_overrides)의 문제

- 보정 22건(baseline 9 + 에이전트 13)을 **모두 Claude가 사용자 위임으로 했고, 모두 점수를 올리는 방향이다.** 사람 확인이 필요하다.
- 에이전트 보정 원칙("가이드북에 있는 사실은 덧붙여도 감점하지 않음, 지어낸 조건은 틀림")을 baseline에 적용해도 바뀌는 문항은 없다. Baseline이 덧붙인 내용은 실제로 지어낸 것이었다.
- **고령·고위험(G5) 4건은 결과를 본 뒤 정답 기준을 바꾼 것이다.** 질문은 65세 이상만 묻는데 정답에 심혈관계 고위험군과 악성종양 위험군까지 필수로 들어 있어서다. 리뷰어가 가장 문제 삼을 부분이다.
- 판단이 갈리는 보정: FIL ANC "미만" → 맞음, VEDO SC 유지 기준 2건(일부러 묻지 않은 평가 시점이 답에 들어감).

## 7. 남은 일 (우선순위 순)

1. **원문을 받는 채점자로 두 쪽 모두 다시 채점** (추천 1순위)
   - 채점자에게 문항의 `원문`과 해당 가이드북 쪽을 함께 준다. "덧붙인 내용이 원문에 있으면 감점하지 않는다"로 규칙을 바꾼다.
   - 열쇠에 척도 범위(Mayo 0~12, 내시경 subscore 0~3)를 넣는다.
   - G5 4문항은 문항 파일의 정답 기준을 고치거나, 고치지 않고 원판정을 유지한다. 둘 중 하나를 정해야 한다.
   - 결과를 본 뒤 하는 수정이므로 **기존 채점 점수와 함께 보고한다.** 그러면 손 보정 22건이 대부분 필요 없어진다.
2. **사람 일치도 확인**: 새 채점 결과로 `human_check.csv`('부분' 전부 + 나머지 무작위 20%)를 뽑아 사람(가능하면 임상의)이 판정하고 κ를 낸다. 지금 human_check.csv는 두 쪽 모두 비어 있다(baseline 38행, 에이전트 42행).
3. **반복 실행**: 조건마다 3회 실행해 평균과 편차를 낸다. Baseline 시험 실행에서 5문항 중 2문항의 정답 여부가 실행마다 바뀌었다.
4. **생성 오류 원인 검증 (어블레이션)**: 저장된 상위 5개 쪽(`answers.jsonl`의 `sources`)을 고정하고 프롬프트만 바꿔 다시 답을 받는다. 바꿀 조건은 (1) 현재 프롬프트, (2) "핵심만" 대신 "원문 조건을 생략하지 말 것", (3) (2)에 "투여 대상 기준과 평가 기준을 구분할 것"을 추가한 것이다. 시험 문항을 보고 고친 프롬프트는 본 결과가 아니라 어블레이션으로만 보고한다.
5. **C형 문항 설계** (환자 적용)
6. 논문에 적을 한계: 이전 치료 질문의 "실패해야" 문구가 주는 혼란, 문항당 1회 실행, 채점자와 평가 대상이 같은 회사 모델, CSV가 원문 PDF와 같다는 가정.

**지켜야 할 원칙**: 평가 문항을 보고 에이전트(검색 방식, 프롬프트)를 고치면 그 결과를 본 결과로 쓸 수 없다. 고친다면 별도 버전으로 명시하고, 그 문항을 보지 않고 만든 문항 세트에서 평가한다.
